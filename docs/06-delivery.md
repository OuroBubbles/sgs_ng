## 可读性与工具

第一批代码采用 TypeScript strict，开启 `noUncheckedIndexedAccess`、`exactOptionalPropertyTypes` 等检查。公共接口使用类型化结果，不依赖空字符串、false、null 混合表达不同失败原因。未知外部数据先验证再进入类型世界。

ESLint 使用 typescript-eslint 的类型感知规则，重点包括漏 await、错误 Promise 使用、未穷尽分支和依赖越界。规则/内容目录将 `no-floating-promises` 的 `ignoreVoid` 设为 false；不能通过 `void ctx.damage(...)` 掩盖结算未等待。[规则文档](https://typescript-eslint.io/rules/no-floating-promises/)

静态规则只能阻止可识别的常见错误，不能证明任意闭包纯净，也不能证明全部异步执行确定。纯查询与调度契约仍需代码评审和行为反例验证。

Prettier 统一缩进、引号、换行、尾逗号；建议 2 空格、100 列、LF、单引号。格式工具不会代替逻辑分段：条件守卫、准备数据、询问、提交、后续效果之间保留必要空行；不机械规定每句之间空行。配置选项见 [Prettier 文档](https://prettier.io/docs/options)。

注释重点解释：规则依据、可变边界、顺序原因、取消后的结果和不变量。公共类型/操作用 TSDoc；复杂流程头部注明输入、结果、开放窗口与善后。禁止用长注释掩盖含混命名，也不追求没有语义价值的注释覆盖率。

不默认限制函数长度或复杂度数字。复杂技能可以长，但一个函数应围绕一个完整语义；共同机制明确后再提取，避免每个技能先套五层模板。

| 检查           | 负责证明什么                                          |
| -------------- | ----------------------------------------------------- |
| `typecheck`    | 类型与公共接口一致；示例 SDK 代码纳入检查后才称可运行 |
| `lint`         | await、纯查询、依赖边界和常见错误                     |
| `format:check` | 格式一致，不代表行为正确                              |
| 领域单测       | 单个操作与结果语义                                    |
| 场景测试       | 多技能、多时点、嵌套和边界行为                        |
| 属性测试       | 移动守恒、状态不变量；只用于真实适用处                |
| 客户端验证     | 真实输入、投影、动画与选择界面                        |
| 平台验证       | 安装、启动、生命周期与真机性能                        |

已提供 package.json、TypeScript/Svelte 检查、ESLint、Prettier、Vitest 与 Playwright 命令，并锁定依赖。P0 覆盖客户端演示；首批规则机制新增无 UI 场景测试，覆盖嵌套、决策、窗口、原子移牌、处理区与伤害骨架。完整领域场景、属性测试和平台验收仍需逐项实施，详见 [P0 记录](07-p0.md) 与 [内核实施](10-kernel.md)。

## 不变量与反例矩阵

| 场景                       | 必须证明的行为                                                   |
| -------------------------- | ---------------------------------------------------------------- |
| 两个 Room 同时存在         | 无共享当前事件、随机源、次数或技能实例状态                       |
| A 技能触发 B，B 再触发 C   | 子结算完整结束后父结算恢复；原因链和事实顺序都正确               |
| 同时点多个技能             | 顺序可预测；玩家可选顺序的范围明确；一次 occurrence 不重复发动   |
| 前一技能令后一技能失效     | 候选执行前重查资格；不重复询问失效技能                           |
| 开窗后新获得技能           | 按默认策略下次窗口生效；显式补入不得无限重触发                   |
| 装备移走产生后效           | 使用离场快照生成遗留实例，不要求仍装备着它                       |
| 增伤、减伤、白银狮子       | 当前草案在最终提交前仍可修改；事实提交后不被篡改                 |
| 连环与不同防具             | 每个目标独立草案；传播使用规则指定快照，不受前一目标局部改写污染 |
| 防止伤害与失去体力         | 不误触发同一组伤害后技能；结果区分防止、零伤害和实际扣血         |
| 濒死、救援、死亡与后效     | 顺序符合选定规则文本；死亡不粗暴终止所有已产生效果               |
| 多目标牌、目标转移与无懈链 | UseId 和 EffectId 正确；取消范围明确，转移不得自循环             |
| 交换两人的手牌/装备        | 提交前完整校验；任何回调不能读到半交换状态                       |
| 实体牌移动                 | 每张牌恰处一处；批内无重复；区域次序与事实一致                   |
| 零材料/多材料转换          | 均能作为合法动作；实际支付与语义牌分离                           |
| 处理区材料被技能获得       | 最终只清理剩余材料，不复制或吞掉已转移的牌                       |
| 观星排序与分组             | 输入集合与输出集合严格一致；顺序、私有可见性正确                 |
| 联合选择与取消             | 部分选择可继续；最终非法组合被拒绝；取消不误付费                 |
| 旧回复/重复回复/无候选     | 请求只结束一次；不产生第二次写入；不挂死                         |
| 费用与发动次数             | 选择取消不计数，规则定义的支付节点恰记录一次                     |
| 额外回合/跳过阶段          | scope ID 独立，临时状态在指定边界结束                            |
| 运行异常/规则中止          | 分别冻结诊断/正常善后；无悬挂 Decision                           |
| 固政类历史查询             | 同时满足过去发生条件与当前牌位置条件                             |
| 显示暗牌、公开后再洗入牌堆 | 不能从投影得到当前未知身份；记忆与当前定位分开                   |
| 动画开启/关闭/加速         | 相同输入产生相同规则结果，选择不会操作过期视图                   |
| 同种子、相同内容和回复     | 轨迹一致；不同运行环境下的确定性另行实测                         |

测试检验用户可见的领域后果与不变量，不仅断言某个内部方法被调用。首批内容选择用来冲击抽象边界，不以武将数量或 PASS 数量证明架构优秀。

## 分阶段实施

| 阶段              | 产物                                                 | 退出条件                                                               |
| ----------------- | ---------------------------------------------------- | ---------------------------------------------------------------------- |
| P0 技术纵切       | 最小客户端、单个选择交互、Spine 资源、Tauri 双端构建 | Windows 与 Android 真机离线可运行；记录具体版本、设备和表现数据        |
| P1 规则骨架       | World、Flow、Window、Decision、commit、scope、轨迹   | 无 UI 完成嵌套、取消、重复回复、原子移动和两个 Room 的关键反例         |
| P2 规则与作者验证 | 回合、用牌/响应、伤害/濒死；少量有明确文本版本的技能 | 武圣、巧变、观星、遗计、白银狮子等机制以普通代码表达，无技能名特判内核 |
| P3 可玩的单机纵切 | 基本模式、双端战场、选择器、立绘/Spine、日志         | 从开局到胜负完整操作；触控与桌面交互通过；可关闭动画验证同结果         |
| P4 内容扩展       | 内容包文档、更多牌/武将、开发诊断                    | 外部作者只依赖 SDK 即可编写并测试复杂技能                              |
| 后续              | 联机、重连、智能托管和完整录像                       | 根据新需求单独设计与验收                                               |

P0 已证实桌面客户端与双端构建可行，Android 真机验收等桌面完成之后开展。按当前“离线规则优先”的目标，未连接 Android 设备不阻塞无 UI 的 P1/P2 开发，但不能因此将 P0 标为通过。P1/P2 一旦发现抽象无法表达某个真实技能，应修正契约并补反例，不通过给核心添加该技能 ID 特判绕过。

P3 当前默认一名人类固定控制甲席，其余角色通过现有正式决策使用信息受限的基础 AI；暂停或后台藏牌并等待明确继续。手动演练保留多席交接，供内容调试使用，详见 [26](26-basic-ai.md)。基础策略与脚本化验收不代表高级智能托管已经实现。

## 现在做与以后做

现在固定：所有权、普通 async 内容、窗口顺序、草案/事实、最终验证、作用域、基础隐藏信息投影、双端 Spine 验证路线。

现在不做：旧包兼容、多语言技能桥、完整事件溯源数据库、任意 await 续局、分布式房间、热更市场、沙箱、通用 ECS、全量规则配置语言、AI 搜索框架。

投影初期只做当前可见信息与规则明确需要的记忆。曾公开的牌面与“现在确定还在某区域”分开表示；洗牌、秘密转移不能凭旧身份持续追踪未知位置。复杂概率知识推断留待 AI 阶段，不为了未来 AI 先建庞大认知模型。

“SoTA”在这里是持续验收目标：新增复杂机制时是否仍能保持清晰语义、作者是否容易定位错误、规则结果是否可复现、双端表现是否经实测成立。语言与架构图本身不能证明这些目标已达成。
