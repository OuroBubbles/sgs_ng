# 04 · 事件与结算契约

状态：整体结算契约。首批串行 Flow、候选快照 Window、Decision、原子提交、处理区与伤害骨架已有运行证明，详见 [10 · 内核实施](10-kernel.md)。本文的完整伤害、联合选择、目标计划、状态与窗口补入策略仍有未实现部分，不能整体当成现成 API。规则包可以扩展流程与时点，但必须明确输入、可变字段、结果、顺序和失效行为。

## 1. 先让普通代码成立

技能可以调用 `await ctx.draw(...)`、`await ctx.damage(...)`，使用任意函数、分支、循环和局部闭包。调用子结算时，父结算挂起；子结算及其嵌套触发处理完毕，父结算才恢复。

每次调用使用显式 `ctx` 派生子上下文，携带当前 Flow、作用域和原因。不能在异步恢复后依赖全局可变的“当前事件”。核心不重写函数体、不生成 step 标签、不强迫技能成为数据表。

规则写操作必须 `await` 或直接返回其 Promise；不允许以 `Promise.all` 并行修改同一局状态。ESLint 防漏 await，运行时开发检查用于发现同一上下文产生未等待的兄弟写操作。JavaScript 的单线程不会自动消除 await 间的逻辑竞争。

## 2. Flow 结果和中断

| 结果        | 语义                                                     |
| ----------- | -------------------------------------------------------- |
| `resolved`  | 流程按契约完成，携带领域结果                             |
| `prevented` | 规则阻止本次效果，之前已支付的费用是否保留由领域规则定义 |
| `skipped`   | 阶段或步骤未执行，不等同于执行后效果为零                 |
| `aborted`   | 父作用域终止、对局结束等导致剩余流程不再继续             |
| 未捕获异常  | 内容/引擎错误；冻结本局并输出诊断，不伪装成正常取消      |

取消选择、阻止伤害、跳过阶段、结束回合是不同动作。领域接口必须显式命名，不能共用一个意义随调用点变化的 `cancel()`。

取消/中止不能撤回已经完成的子结算。要终止一个尚在等待的 Decision，运行时将其关闭并使等待返回终止结果；普通 Promise 不会因为一个 flag 自动停止。所有规则入口和 await 恢复点检查作用域是否仍有效，已关闭上下文的写操作必须被拒绝。

对象死亡不自动意味着所有关联流程都中止：死亡角色的已经产生的牌效果、遗留效果可能仍要结算。流程声明继续条件，通用运行时只负责执行它；不能全局添加 `if dead return`。

## 3. Window 不是普通发布订阅

一个 Window 有类型化的 payload、允许的修改接口与模式指定的顺序策略。打开窗口的 Flow 必须等待窗口完成。UI 通知不能成为规则触发入口。

默认规则窗口算法：

1. 开窗时确定行动顺序锚点与当前已登记的触发实例集合，形成候选快照。候选身份包含技能实例、效果 ID 和 occurrence ID。
2. 按规则定义的阶段/顺序组处理，再按座次；同一玩家同组多个可发动效果允许其选择顺序，自动项采用稳定 ID 顺序。
3. 轮到候选时重查资格；不再合法则跳过。询问返回后、支付前再查相关条件。
4. times 在开窗时固定有限次数，每个来源只开放最早合资格的一次；一时不合资格的未处理身份可在同席其他效果后重查。选定该来源时才正式跳过其失效前缀；已拒绝、完成或明确跳过的身份不回头。没有可执行者时收束当前组/席位。实现与组合反例见 [38](38-window-occurrences.md)。
5. 一个候选的子结算完成后，继续本窗口。后续候选读取最新状态；已经过去的座次和已处理 occurrence 不回头。
6. 窗口期间新获得的技能默认从下一窗口生效；若某条规则要求当前窗口补入，必须显式 enqueue 新 occurrence，并记录原因，禁止隐式无限发现。

这是新项目的默认语义选择，不冒充所有三国杀版本的唯一规则。模式可替换有名的窗口顺序策略；不得让作者凭空填 `9999` 与别人的技能抢优先级。只有真实规则冲突才增加顺序组，并写反例测试。

“装备离场时”允许从提交前快照产生遗留触发实例，该实例不依赖提交后角色仍拥有装备技能。普通触发则默认重查拥有/有效性。这两个情况需要通过触发来源类型区分，不能为装备离场规则全面关闭资格检查。

## 4. 草案与提交

**草案可改，事实不可改。** 技能通过 `damage.adjust(...)`、`use.replaceTarget(...)` 等少量领域方法修改草案，附带原因；不开放任意字段写入。无需把每个加减数操作变成全局“贡献对象”体系。

一次 `commit` 是短小、同步、不可 await 的状态变更边界：验证前提和不变量，准备完整变更，再一次性应用并追加事实。内容回调、资源加载、选择和触发均不能在提交中执行。检查失败则整个提交不生效。

这不是整个技能的数据库事务。支付费用、弃牌触发、摸牌、伤害可以是多个合法的提交；中途代码出错不自动把整条链倒放。运行错误停止对局并保留已提交轨迹，避免吞错后继续污染状态。

动作返回领域结果，例如支付是否成立、牌实际去了哪里、伤害是否被防止。调用者不得用“Promise 正常返回”推断效果一定成功。

## 5. 伤害标准流程

建议基线如下；伤害是领域流程，不是核心强制所有事件拥有的阶段模板。

```text
创建 DamageDraft
  → damage.causing          来源侧修改
  → 保存来源阶段快照        若连环等规则需要
  → damage.inflicting       目标侧修改、防止或转移
  → 校验最终目标和数量
  → 提交本次伤害与体力/护盾变化
  → 必要的濒死与救援子流程
  → damage.dealt / received 已提交结果上的后效
  → damage.settled          本次流程收束
  → 按模式策略处理连环传播等后续子流程
```

规则库必须进一步固定：护盾结算方式、濒死与受伤后时点顺序、来源死亡处理、传播目标快照时机。上图是项目建议基线，不是两份参考代码的混合复刻。

`DamageDraft` 包含当前来源、目标、数量、属性、关联用牌和传播标识。所有防御窗口结束前，当前数量都可按契约修改；不得提前冻结导致白银狮子一类防御技能无法生效。

`DamageResult` 区分名义输入、最终伤害值、护盾消耗、实际体力损失、是否防止、传播来源等。触发技能明确使用哪个量，不能把 `amount` 一律解释成扣血数。

若连环规则需要某一阶段的数量，应读取不可变的来源快照；每个目标有独立草案，不能共享被前一目标防御改写的对象。目标转移同样需规则明确是否重开来源侧窗口及如何避免转移环，不能偷偷把旧对象的 `to` 改掉继续跑。

连环的实际实施已在 [45](45-chain-damage.md) 固定：提交时收集目标计划，原子扣血与解链，变更窗口/濒死/后效/收束后逐个传播；本项目用起点最终 amount 作为基数，保留来源阶段快照供其他规则读取。传播来源是稳定伤害 ID，各目标分别结算；护盾与转移仍未实现。

`damage.settled` 表示本次命中的结果已收束；若当前伤害流程负责传播，外层 `await ctx.damage(...)` 仍须等所有传播子流程完成才返回。时点名称不能被误当成整个调用已经退出。

## 6. 卡牌与移动

实体牌拥有唯一 CardId，且恰处于一个区域。虚拟牌是本次使用/响应的语义值，记录牌名、属性、材料 CardId 列表和转换来源；零材料和多材料都是正常情况，不额外塞进实体牌堆。

用牌冻结本次牌面解释，保留实体材料的独立身份。一次 `UseCard` 有稳定 UseId，每个目标效果有自己的 EffectId；取消一个目标不取消整张牌，响应一次效果也不意味着完成整张多目标牌。

用牌标准流程为：生成并校验用牌意图 → 在宣告提交中支付材料、登记次数与本次牌面 → 处理宣告后效 → 目标确认窗口 → 按目标效果逐一开放响应并结算 → 用牌结束时点 → 处理区善后。提交前允许取消选择；提交后取消某个效果通常不退材料和次数，特殊规则须明确覆盖。

目标列表不是随处可变的数组。增删或转移目标通过 UsePlan 方法完成，明确重新校验哪些目标、哪些目标已确认、哪些已经结算。默认新增目标只进入尚未完成的效果队列，已结算目标不隐式重跑；要求再次结算时创建显式的新 EffectId。每个目标轮到时重查其有效性。

【闪】式响应和【无懈可击】式反制由不同响应窗口策略承载：前者满足指定效果的响应要求，后者可以产生新的反制子流程。规则库记录被响应的 EffectId，按该牌/模式规定的询问顺序与终止条件结算；不靠翻转一个全局 `cancelled` 标志处理整条无懈链。更换模式可更换响应策略，核心无需知道卡牌名字。

材料先经规则移动到处理区，再结算效果；其他技能可以合法取走其中一部分。结尾只清理仍属于本次处理作用域的剩余材料，不能把所有原材料无条件弃置。虚拟装备需区分 EquipInstanceId 与材料牌，直到装备实例解除。

移动批次包含每张实体牌的起点、终点、顺序、原因和可见性。交换手牌/装备等语义整体应先验证所有移动，再一次提交，随后派发离场/入场后效；回调不能观察到“牌已离开 A，却尚未到 B”的半完成交换。

若规则确实要求中间处理区可见并触发，那是两个显式批次，不用“原子性”抹去合法时点。附属牌区绑定装备实例或状态实例，而不是靠扫描父事件猜它属于哪次迁移。

## 7. Decision 与联合选择

选择会话分为三部分：

- `DecisionSpec`：参与者、提示、选择类型、可显示数据、取消策略、request ID；可序列化。
- `DecisionRuntime`：查询、候选生成、部分选择检查、最终验证的普通函数/闭包；只活在执行侧。
- `DecisionReply`：稳定 ID、顺序和选项组成的值；不带 DOM、函数或直接可写实体引用。

四种校验职责：

1. 候选生成：哪些元素可能参与选择。
2. 部分选择：当前前缀是否仍有完成可能，不把尚未满足最终条件等同于无效。
3. 组合检查：牌、目标、选项的关联约束，如颜色各异、点数和、对不同目标分配不同牌。
4. 最终验证：提交时基于最新状态与草案完整验证，包括所有权、次数、费用和目标合法性。

UI 高亮调用同一选择会话的纯查询。不能穷举所有组合，也不能逼作者把任意闭包翻译成 DSL。普通选牌、选人、排序、分组可由标准面板表示；特殊选择可以扩展展示组件，最终规则仍由执行侧验证。

预览带有会话内递增 token，同时反映 World 与草案变动；单个 World revision 无法代表尚未提交的目标变化。提交必须匹配仍开放的请求，旧回复/重复回复不会产生第二次效果。无候选时返回明确的 unavailable 或按规则跳过，不能无限等待。

支付操作在选择后重新核验并返回 `paid/unavailable` 等领域结果。若规则要求费用与“宣告发动”不可分，应在同一同步提交中登记费用、次数和发动标记，再触发支付后效；不把完整技能效果捆成事务。费用被替代时是否仍算支付成功，由该费用契约定义。

## 8. 作用域、状态和清理

临时效果绑定有身份的 scope：本次用牌、阶段、回合或明确的后续时点。额外回合/插入阶段都拥有新 scope ID；不使用字符串后缀或一个全局 turn 计数近似有效期。

清理分两类：

- 运行时释放：关闭决策、注销临时监听、释放句柄，幂等，在 `finally` 中完成。
- 规则善后：剩余处理牌去向、状态到期后的效果，可能产生新的结算；由领域流程显式 await，并遵守正常/中止不同策略。

正常完成、跳过和规则中止要执行规定的善后。未捕获代码错误时只做安全资源释放并冻结现场，不继续发动一长串未知后效。故障现场不保证是一局可继续玩的合法对局。

## 9. 查询和确定性

距离、手牌上限、使用次数、禁止、牌面解释由具名纯查询计算；查询不能 await、改状态或抽随机数。不同查询明确自己的组合规则，例如上限先基础值再增量再下界约束，禁止查询默认任一禁止成立即拒绝；不建立一个“全部 modifier 通用加法”框架。

随机操作使用每局注入的随机源；稳定排序有明确的 ID 破平规则。技能不得依赖 `Math.random`、真实时间、动画帧和未记录的外部 I/O 决定结果。此约束服务复现和测试，靠 lint 与约定执行，当前不做安全沙箱。

每次记录同时保留原因链和单调序号。查询“本次弃牌阶段弃置且目前仍在弃牌区”时，先按 scope 读历史，再查当前位置；不要通过父链层数和 UI 元素判断游戏语义。
