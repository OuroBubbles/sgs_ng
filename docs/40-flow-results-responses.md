# 40 · 流程结果与响应边界

本批审计标准牌、普通响应、委托供牌、改判和救援的衔接。修正决斗吞掉响应流程中止、部分支付/打出窗口默认从首席开始，以及救援桃的底层目标校验；同时提供同步的 `Context.unwrap`，减少作者重复传递中止的样板代码。它不改变技能作为普通函数的设计。

## 两层结果，显式选择是否继续传播

运行层的 `FlowResult<T>` 仍只有 `resolved(value)` 与 `aborted(reason)`。一次正常完成的领域操作可以返回 `declined`、`unavailable`、未支付、零伤害等业务结果，它们不等于运行层中止。代码异常仍按故障处理。

作者需要延续中止时，可以写：

```ts
const response = ctx.unwrap(await book.respond(ctx, responder, ['standard:slash'], effect));

if (response.kind !== 'responded') {
  // 正常拒绝或没有可用杀：按决斗规则处理。
}
```

[Context.unwrap](../src/core/runtime/room.ts) 是同步方法，只接收已经完成的 `FlowResult`，不接收 Promise，也不启动额外 Flow。`resolved` 直接返回业务值；`aborted` 用原原因中止当前调用者的作用域。它检查当前上下文仍可写且没有正在等待的子操作；不能在纯查询中调用，也不能唤醒已关闭的上下文。

仍然可以直接检查 `await ctx.flow(...)` 的结果，以明确恢复或执行领域善后。只有选择 `unwrap` 的调用层才继续传播中止，不把某个子技能的中止一律升级为整局结束。`room.abort`、正常终局和代码故障的原有契约保持独立。

例如一个处理区 body 中止后，`withProcessing` 先执行规则善后并清理余牌，再把 `aborted` 返回给父调用者；父调用者此时可选择恢复，或 `ctx.unwrap(result)`。已经提交的宣告、支付、打出和移动都不回滚。普通异常不会被包装为可恢复的 `aborted`，最初故障的原因链保持不变。

已在标准杀/群体攻击的响应骨架、标准救援、决斗、桃、无中生有、八卦阵和演武包中采用这个入口。没有声称所有历史作者函数都已完成同类审计；只有在确实需要传播运行中止的调用处使用它，领域上的失败仍由作者按规则判断。

## 决斗：中止与未打出杀分开

旧决斗用一个条件合并了 `response.kind !== 'resolved'` 与业务上未打出杀，可信规则扩展返回局部中止时，会错误地继续造成伤害。

现在先解包运行结果，再判断是否实际打出。响应流程中止会中止当前目标效果，保留原原因；已经打出的第一张杀照常成为事实并完成处理区善后。无双要求连续两张杀时，第二张流程中止也遵循这个边界。

这不等于取消整张牌。多目标扩展中，前一个目标效果中止，后一个已确认的目标仍按既有目标调度继续结算；后者确实没有杀时照常受伤。普通主动放弃或没有可用杀仍属于正常未响应，不能因引入 `unwrap` 而全部变成中止。

测试使用可信规则扩展的 `CardBook.respond` 返回真实 `ctx.flow(...abort...)`，保留实际 World、支付、已提交响应和标准决斗 resolver，没有把界面“放弃”伪装成运行中止。

## 明确回合外领域流程的事件主体

`actor`、最初受益者和被判定者不能互相代用。本批为明确拥有单一执行者的领域调用补齐显式锚点；下列座次测试均处于没有活动回合的独立流程中，验证回合外的起点：

| 窗口                                       | 行动序起点               |
| ------------------------------------------ | ------------------------ |
| 支付产生的 `cardsMoved`                    | 已提交支付凭据的 `actor` |
| `costPaid`                                 | 已提交支付凭据的 `actor` |
| 普通/委托响应的 `responseFinished`         | 实际打出者               |
| 改判产生的 `costPaid` / `responseFinished` | 实际发动/打出者          |
| 独立供牌的 `responseFinished`              | 实际供牌者，保留原有规则 |

例如 c 为 b 供闪，完成窗口中各席位的行动序从 c 开始；不会因为 b 是受益者或 a 是首席而改序。c 为 b 鬼才改判也从 c 开始打出后效；判定揭示、改判机会与判定结束窗口仍属于被判定的 b。

支付后使用冻结的 `receipt.actor`，不在移牌后效结束后重读可变的调用参数。内容闭包即使改写了原输入对象，也不能改变已经提交的实际支付者。

本批不把通用批量移牌强行归给某一个角色，也没有完成所有无明确执行者窗口的排序政策。通用移动、多个受影响角色和模式自定义的顺序仍需单独定义；不从一次支付修正推断全局时点审计已完成。

另已查证本地 [FreeKill 触发循环](../freekill/lua/core/trigger_event.lua) 从 `room.current` 开始轮询。当前项目的领域显式锚点和核心首席默认，并不能直接证明回合内符合这套行动序。本章当时只验收了回合外行为，不能作为回合内标准排序已完成的证据。活动回合优先、模式覆盖和相关衔接现已由 [41](41-action-order.md) 接入并另行验证。

## 桃：救援语境约束真实目标

桃在普通使用语境中治疗自己；在救援语境中只能治疗该请求的濒死角色。救援别人时，受伤的自己不再通过底层目标校验。濒死者使用桃救自己仍然合法。

这项约束位于标准牌定义，继续复用统一目标、支付、回复和濒死流程。救援桃仍是 `card.used`，不是 `card.responded`。界面的救援请求本就固定目标，本次修正补齐规则调用入口，不能用界面没有提供错误选项来代替底层合法性。
