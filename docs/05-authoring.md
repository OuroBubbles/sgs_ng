# 05 · 内容作者接口

状态：完整 SDK 的设计草案。本文示例用于讨论未来作者体验，**不是全部已有 API，也未整体通过类型检查**。当前 SDK 已提供 Context、Window、Decision、触发/主动技能、武将目录、来源、生存期、状态、联合选择、支付与部分领域操作，实际签名和可运行例子见 [10 · 内核实施](10-kernel.md) 与 [12 · 技能/选择/支付](12-skills-selection-costs.md)。转换与具名纯查询已有首批实现，见 [13](13-card-use.md) 与 [14](14-turn-draw.md)；完整查询组合仍待实现，本地模块导入已接入 [47](47-local-content-modules.md)；后文 ctx.owner 等示意写法不等于现有接口。

武将目录与实际主动技能 API 见 [27](27-generals-active-skills.md)。普通源码包登记、依赖/版本校验与可运行演武包现已接入，实际契约见 [39](39-source-packages.md)；后文仍含未来接口示意。

## 内容包与公开接口

内容包是普通 TypeScript 模块，导出 manifest、武将、牌、技能、翻译和资源声明。构建工具编译成 JS；初期在应用构建时登记，作者改完后重新构建即可，不先做安卓动态脚本安装器。

包用 `packageId:localId` 命名内容；manifest 声明依赖和内容版本。声明、依赖与牌/技能引用在创建对局前校验，失败时不留下半注册的对局。独立资源打包和路径审计仍待实现。

对局锁定内容版本。开发时重载发生在下一局或重启场景，不在一条挂起的技能函数中途替换定义。外部内容作者只依赖 `sdk` 公开导出；可以共用普通 TS 辅助函数，不依赖全局 `game` 对象。

本地模块加载已接入 [47](47-local-content-modules.md)：相同源码单独构建，运行时由宿主提供 SDK 身份，开局页导入。持久安装与启动恢复见 [48](48-content-persistence.md)，独立资源目录仍待继续；这是加载方式演进，不是重新设计技能语言。当前不设计签名、权限体系和沙箱。

当前牌面过滤使用 cardQueries.cardFace 与普通 modify；book.face 供材料与规则读取，judge(ctx, book, input) 明确使用本局目录。字段组合、判定主体、封口和 UI/基础 AI 同源契约见 [50](50-card-faces.md)，可运行示例为作者演武的映绯。

## 技能是一组效果

| 效果形态 | 用途                         | 作者需要提供的东西                  |
| -------- | ---------------------------- | ----------------------------------- |
| 触发效果 | 在指定时点参与结算           | 时点、资格、可选发动/费用、执行函数 |
| 主动效果 | 玩家在合适的操作窗口主动发动 | 可用条件、选择模型、费用、执行函数  |
| 转换效果 | 将零到多张材料解释为另一种牌 | 候选与组合约束、生成语义牌的函数    |
| 查询修正 | 距离、上限、禁止、牌面等     | 对具名查询的纯函数                  |

这是标准组合入口，不是封闭继承分类。复杂技能可以组合多种效果，也可直接调用底层公开流程。新规则包可以定义新的类型化 Window 和领域操作；只有出现跨技能复用时才提升为标准 helper。

技能元数据与规则逻辑分离：名称、描述、配音、提示资源不决定规则；翻译不依赖扫描函数源码生成。作者注释解释技能文本版本与特殊裁定，不逐句翻译代码。

## 示例一：受伤后普通控制流

下面是演示技“周济”：受到伤害后，可摸两张牌，再将任意张当前手牌交给另一名存活角色。它不冒充某个历史版本的遗计。

```ts
export const relief = defineSkill({
  id: 'demo:relief',
  effects: [
    on(damage.received, {
      when: (ctx, hit) => hit.target === ctx.owner && ctx.isAlive(ctx.owner),

      async run(ctx) {
        const activation = await ctx.choose.invoke({ skill: 'demo:relief' });

        if (activation.kind !== 'chosen' || !activation.value) {
          return;
        }

        await ctx.draw(ctx.owner, 2);

        // 摸牌本身可能触发其他技能，恢复后重新检查继续条件。
        if (!ctx.isAlive(ctx.owner)) {
          return;
        }

        const choice = await ctx.choose.cardsAndTarget({
          cards: () => ctx.hand(ctx.owner),
          cardCount: { min: 1, max: 'all' },
          targets: () => ctx.otherLivingPlayers(ctx.owner),
          optional: true,
        });

        if (choice.kind !== 'chosen') {
          return;
        }

        await ctx.give({
          from: ctx.owner,
          to: choice.target,
          cards: choice.cards,
        });
      },
    }),
  ],
});
```

`ctx.choose` 是当前技能实例绑定的选择门面；运行时自动附上 request ID、技能来源和作用域。`cardsAndTarget` 是联合选择标准模型，不是两个彼此独立的对话框。`give` 会最终校验并记录实际移动结果；如果后续文本依赖成功交付数量，作者必须读取该结果。

如果需要每点伤害一次，触发入口按已提交结果产生 occurrence；如果需要重复分配，则在执行函数中写循环。不要为了隐藏一个 `for` 创建通用“多段技能配置”。

## 示例二：转换牌只负责转换

以红色牌视为【杀】的配方为例，示意如下；具体可用区域按所选规则版本确定。

```ts
export const redSlash = defineSkill({
  id: 'standard:wusheng',
  effects: [
    viewAs({
      materials: selection.cards({
        from: ['hand', 'equipment'],
        count: 1,
        accepts: (ctx, card) => ctx.colorOf(card) === 'red',
      }),

      makeCard: (_ctx, materials) => virtualCard('standard:slash', { materials }),
    }),
  ],
});
```

转换配方不复制【杀】的距离、次数、目标数量或响应条件。统一用牌/响应服务在当前上下文检查这些条件。材料可选性与“生成牌能否使用”都要校验。

零材料转换必须在没有任何可选实体牌时仍能作为动作候选出现。多材料牌、变花色、变牌名、选择某个牌名再选材料都由选择模型与生成函数组合，不另造一套点击机制。

## 复杂技能应如何写

### 巧变类

在阶段开始前取得显式 PhaseHandle；选择弃牌费用；成功支付并登记跳过意图；支付后效完成后检查继续条件；按阶段分支执行后续选择与移动。阶段主流程看到已跳过状态后不执行本体。

“登记跳过”与费用何时成为事实必须由该技能版本规定，不能随 UI 回调顺序改变。若费用和宣告需原子绑定，调用规则库已有的支付/宣告组合入口。后续询问被取消不自动退回已付费用。

### 观星类

从牌堆取出指定数量的牌，创建有归属的处理作用域；向操作者提供私有排序/分组选择；完整验证每张牌恰好出现一次；按回复提交牌堆顶/底顺序。中止时使用明确的剩余牌归还策略。

现有 ArrangementSelection、私有取牌与显式归还实现见 [37](37-arrangement-astrology.md)。算法与校验在规则端，分组/前后调整在客户端。视图不得因为看见这批牌就取得整个牌堆身份列表。

### 遗计类

按伤害 occurrence 触发；创建暂存牌组；重复询问接收者与子集；每次移动后重新检查剩余牌和继续条件；结束时按技能文本处置余牌。这个流程自然需要 `while`、局部集合与 await，全部保留。

### 固政类

使用显式弃牌阶段 scope 查询相关弃置记录，再筛选当前仍在弃牌区的牌。返还一张与收取剩余牌分别遵从技能文本；后续触发可能改变剩余集合，因此不能缓存第一步的全部有效性直到结束。

### 木牛流马类

附属区域跟随有身份的装备实例。转移装备时，语义移动批次明确附属区域是跟随、清空还是保留；技能读取移动前后快照，不扫描“前一个父事件的某次处理区移动”来猜交换结果。

## 选择能力的最小标准库

优先实现：选项、选牌、选目标、牌与目标联合选择、排序/分组、分配。多步骤流程由作者使用函数串联；标准选择模型可以复用验证器与面板。

复杂约束允许普通函数，例如“选中的牌点数和不超过 13，最终必须等于 13”“两张牌颜色不同，且目标能接收对应装备”。部分选择校验应保留合法完成路径；不把最终验证函数直接拿来禁用所有不完整前缀。

当纯预览读取的信息可能包含暗牌，输出仅能反映规则允许操作者知道的信息。随机抽取未知手牌使用决策内的 opaque choice ID，由引擎映射实体牌；UI 不拿真实身份然后显示背面。

## 状态和生命周期

状态以技能实例/效果实例命名，用类型化数据保存，作用域决定失效时间。一个技能失去后是否保留其已经创建的效果，由状态定义明确；不统一清除全部“来源为该技能”的状态。

可见标记从真实状态派生；界面上有几个标记不能反过来成为规则事实。次数限制记录成功宣告或成功支付等明确节点，而非点击次数；一个技能有多个分支时，可有独立计数 key。

历史接口至少支持按作用域、参与者、牌、操作原因和类型筛选；先做直观查询，确有瓶颈再加索引，不建立面向内容作者的查询语言。

## 调试体验也是作者接口

首批内容开发应配套：一次发动的父子因果、候选被拒绝的原因、伤害数值每次修改的来源、当前处理区牌归属、随机种子与脚本化回复。异常包含包/技能/效果/Flow/Decision 标识及源码映射。

优秀的作者体验不只在“少写几行”，也在于写错时能定位到哪条规则边界。调试器从轨迹读取信息，不要求作者每个技能手写 console 日志。
