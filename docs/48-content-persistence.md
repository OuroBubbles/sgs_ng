# 48 · 离线内容库的持久安装与恢复

更新：2026-10-18。接续 [本地模块](47-local-content-modules.md)，已导入的模块源码和启用选择现在持久保存，刷新或重新启动应用后自动恢复。作者仍交付同一份 .sgs.mjs，不需要新的技能格式。

## 数据与执行各归其位

后续 [66](66-content-resource-bundles.md) 在同一事务/CAS 边界增加 `.sgs` ZIP 和独立 Blob 资源，仍与源码和启用选择同次保存。下文的纯源码字段和“独立资源待继续”为初始实施边界。

[content-storage.ts](../src/app/offline/content-storage.ts) 使用 IndexedDB 的单个 loadout/current 记录，格式为 sgs-content-store/1。记录只包含：

- 非负安全整数 revision。
- 模块 ID、名称、内容版本、文件名和完整源码字符串。
- 用户显式选择启用的包 ID 列表。

函数、SkillHandle、World、决策会话和 Room 均不写入存储。数据解析后复制并冻结，不借用调用者的可变列表。

[ContentLibrary](../src/app/offline/content-library.ts) 协调加载、装配和持久提交。它只持有内容目录，不持有正在进行的对局。恢复时从已保存的源码重新创建模块，传入当前真实 SDK，核对声明的 ID/名称/版本与记录一致，再使用原有依赖、命名空间、牌/技能/牌组检查。

每局仍创建自己的目录与技能实例；内容库恢复不恢复悬停技能、旧实例身份或牌局调用栈。对局参数与进行中的牌局存档不属于本批保存内容。

## 成功提交后再更新目录

导入先在临时目录中完整加载、装配，然后把全部模块源码与启用列表放入同一个 IndexedDB readwrite 事务。只有 transaction.complete 后才发布新开局目录；put 请求成功还不能算保存成功。异常或中止保留此前的内存目录和持久记录。

启用、停用、依赖级联移除和清空遵循同一边界。保存期间开局与其他内容修改被阻止，开关可显示待保存的输入草稿；失败后回到已提交值，错误不会伪装成安装成功。启动读取尚未完成时也不能提前开局。

写入在同一事务内读取当前 revision 并比较预期值。多个窗口同时修改时，旧目录不能覆盖较新记录；错误提示提供明确的“重载”，重新读取后才继续。不会因为另一个窗口更新内容，就热换本窗口正在运行的规则或技能。

## 错误恢复保留证据

模块语法/执行错误、内容版本不符、依赖缺失和损坏记录均不会自动删除已保存源码。首次启动失败时保留默认标准目录，仍可开始标准对局；如果已有可用内存目录，重载失败也保留它。

需要处理错误时，可重载，或明确清空已保存内容。清空包含缓存模块和启用选择，不修改作者原文件。已能读取版本的清空仍受并发版本检查；对于无法解析的记录，恢复分支只允许清除仍然损坏的值。如果另一个窗口已修复成有效新记录，旧窗口必须先重载，不能误删新目录。

本地存储不可用、额度不足或事务中止会明确失败。没有静默改成仅当前窗口安装，也没有忽略保存失败后宣称重启可用。

## 真正的程序重启验收

[verify-windows.ps1](../scripts/verify-windows.ps1) 现在验证两个不同的原生进程：

1. 启动当前 exe，完成完整 WebView2 场景，通过真实文件输入安装渡口模块，等待持久提交完成。
2. 终止并确认第一个进程结束，等待其 CDP 监听关闭。
3. 用同一个 exe 与同一测试数据目录启动第二个进程。[重启驱动](../scripts/smoke-content-restart.mjs) 不再选择文件，核对缓存源码哈希、启用状态及新的进程 ID。
4. 真实新开 seed 2 的渡客对局，使用备航、发动潮声，核对宿主窗口、手牌净增和材料消耗；随后清空并刷新，确认移除也持久化。

这项证据区别于仅刷新网页。原生报告分别为 `.artifacts/ui/native-smoke-<build>.json`、`native-content-restart-<build>.json` 和 `native-profile-<build>.json`，记录 exe/模块哈希、两个进程身份、实际数据目录与结果。

验收使用一次性、独立的 WebView2 数据目录，避免测试的导入/清空影响正常内容库。环境覆盖机制来自 [Microsoft WebView2 官方接口说明](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/webview2-idl)；脚本还检查属于当前应用的 WebView2 子进程命令行，确认实际 user-data-dir 落在本次生成的目录中，才开放测试操作。两个原生进程共用同一测试目录。

清理仅针对 `.artifacts/ui/webview-profile-<build>-<guid>`：先核对绝对路径、目录名和占用进程，再由同一 PowerShell 脚本删除；不读取或清空正常应用的数据目录。发布脚本要求重启报告及数据目录证明都与本次 exe、模块和进程身份对应。
